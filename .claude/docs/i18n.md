# Internationalization (i18n)

Custom, store-based i18n living in `src/i18n/`. No library. All UI text is read directly
from a typed dictionary - there are no string keys and no runtime key lookup.

## Reading text in components

Import the `t` store from `$i18n` and read the dictionary directly:

```svelte
<script lang="ts">
	import { t } from '$i18n';
</script>

<h1>{$t.header.home}</h1><p>{$t.faq.title}</p>
```

`t` is a derived store of the **active locale's** dictionary, so every `$t.…` re-renders
when the locale changes. Arrays are read as arrays (`{#each $t.faq.items as item}`), and
text containing markup is rendered with `{@html …}` (e.g. FAQ answers).

### Dynamic strings are functions

Any string that interpolates values is a **function taking a single options object** and
returning the final string:

```svelte
{@html $t.portfolio.pagination.page({ current: currentPage, total: totalPages })}
{@html $t.portfolio.dates.label({ fromDate, toDate })}
```

Define them the same way in the dictionary (English annotates the parameter object; other
locales infer it):

```ts
// en-US.ts
page: ({ current, total }: { current: number; total: number }) =>
	`Page <b>${current}</b> of <b>${total}</b>`;
```

## The dictionaries

Translations are plain `as const` TypeScript objects, one file per locale in
`src/i18n/translations/`:

- **`en-US.ts` is the single source of truth for the shape.** It is authored `as const`,
  so its literal types fix which keys exist, how long each list is, and the signature of
  every dynamic-string function. From it we derive the contract:

  ```ts
  export type TranslationDictionary = DeepWiden<typeof enUS>;
  ```

  `DeepWiden` (in `model.ts`) widens literal values (`'Home'` → `string`) but keeps keys,
  tuple lengths and function signatures.

- **Every other locale must fulfil that shape:**

  ```ts
  export const plPL = { … } as const satisfies TranslationDictionary;
  ```

  A missing key, an extra key, a list of the wrong length, or a dynamic-string function
  with the wrong signature is a **compile error**. `npm run check` is the gate.

### Editing / adding translations

1. Change **English first** - it defines the shape. Add the key, list entry, or function.
2. `npm run check` will now flag every other locale that no longer satisfies the shape.
3. Fix each locale until it passes. To add a whole locale, create
   `translations/<code>.ts` (`as const satisfies TranslationDictionary`) and register it
   in `i18n.ts` + the `Locale` enum.

## Structural data vs. text

`model.ts` files hold only **structural** data (urls, image paths, dates, links, css
classes), keyed by the same keys as the dictionary. The text lives in the dictionary and
is read by that key. Examples:

- Portfolio items carry url/dates/labels/media urls; their text is
  `$t.portfolio.projects[item.key]`. The `key` field is typed
  `keyof TranslationDictionary['portfolio']['projects']`, so a typo is a compile error.
- Where a `model.ts` holds an array that must line up with a dictionary array (e.g.
  `SERVICE_CARD_IMAGE_SRCS` ↔ `$t.services.cards`), the two are index-aligned - keep them
  the same length and order.

## Locale state & switching

- `currentLocale` is a writable store (default `en-US`), persisted to local storage and
  initialised from the stored value / `navigator.language` in the root layout.
- `LOCALES_MAP` (in `model.ts`) holds each locale's `label` and `flag` (a path to an SVG
  in `static/flags/`, **not** an emoji).
- The language selector is `src/lib/Header/LocaleSwitcher.svelte` - a custom dropdown
  (native `<option>` cannot contain the flag `<img>`).
